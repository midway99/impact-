# AGENTS.md

Инструкции для AI-агентов и разработчиков, работающих с проектом **impact**.

## Обязательные правила задания

Это условия приёмки. Нарушение любого пункта — ошибка, даже если код работает.

1. **Локальный проект со сборщиком** — **Vite** (допустим Webpack, но выбранный сборщик один, не смешивать).
2. **TypeScript** в режиме `strict`, с использованием доступных типов (включая типы библиотек) и **ООП**.
3. **GitHub-репозиторий** заведён под задачу, фичи пушатся **по ходу выполнения**, а не одним коммитом в конце.
4. **Никаких лишних аллокаций** — особенно в коде, выполняемом каждый кадр; **никакого дублирования кода**;
   **никаких god-классов и god-методов**.

## Стек и команды

- Сборка: Vite + TypeScript, менеджер пакетов — `npm`.
- Рендер/физика (если задание 3D): `@babylonjs/core`, при необходимости `@babylonjs/gui` и Havok (`@babylonjs/havok`,
  Physics V2: `HavokPlugin`, `PhysicsAggregate` / `PhysicsBody`, `PhysicsConstraint`). Версии `core` и `gui` совпадают.

```bash
npm install       # установка зависимостей
npm run dev       # dev-сервер
npm run build     # tsc --noEmit && vite build
npm run preview   # просмотр production-сборки
```

`npm run build` обязан проходить без ошибок и без предупреждений типов **перед каждым коммитом**.

## Git и GitHub

- Отдельный репозиторий под задачу; `main` всегда собирается.
- Один коммит — одна законченная мысль. Сообщения в императиве: `add impact detector`, `extract effect pool`.
- Фича готова → коммит → **push сразу**. История должна показывать процесс: каркас, затем фичи по пунктам ТЗ.
- Не коммитить `node_modules/`, `dist/`, `.env`, личные конфиги IDE.
- Не затирать чужие незакоммиченные изменения: перед рискованными операциями проверять `git status`.

## TypeScript

- `tsconfig.json`: `"strict": true`, `"noUnusedLocals": true`, `"noUnusedParameters": true`, `"noImplicitReturns": true`,
  `"noFallthroughCasesInSwitch": true`, `"verbatimModuleSyntax": true` (импорт типов — только через `import type`).
- Запрещены `any`, `@ts-ignore`, `as unknown as` без письменного обоснования в комментарии рядом.
- Публичные поля и методы — с явными типами; модификаторы доступа (`private` / `protected` / `public` / `readonly`) ставить всегда.
- Фиксированные наборы значений (состояния, режимы, направления) — `enum` или union-типы, а не «магические» строки и числа.
- Импорты из Babylon.js — точечные (`import { Vector3 } from "@babylonjs/core/Maths/math.vector"`), чтобы работал tree-shaking.
  Если метод сцены «не существует» (например `scene.enablePhysics`) — не подключён модуль с побочным эффектом,
  который его регистрирует.

## ООП и архитектура

- **Один класс — одна ответственность.** Если описание класса требует союза «и» — его надо разделить.
- Ориентиры размера: класс — до ~200 строк, метод — до ~30 строк, аргументов — до 4. Превышение = повод выделить класс/метод.
- Зависимости передаются через конструктор (composition over inheritance). Глобальных синглтонов и мутабельного
  глобального состояния нет.
- Точка входа (`src/main.ts`) только создаёт корневой объект приложения и запускает его — никакой логики.
- Все константы (размеры, массы, скорости, пороги, цвета) — в одном типизированном конфиге (`src/core/GameConfig.ts`),
  а не разбросаны по коду.
- Общие контракты — интерфейсы; `metadata` мешей — типизированный объект с `id`, а не произвольный `any`.
- Ввод/UI не трогают физические тела и материалы напрямую, а вызывают методы сущностей.

Ориентир по структуре (заводить папку, когда в ней появляется второй файл):

```
src/
  main.ts          # только создание корневого класса и старт
  core/            # App/Game: движок, сцена, рендер-цикл, владение сущностями; GameConfig
  scene/           # камера, свет, окружение
  physics/         # загрузка движка, фильтры коллизий, базовые физические сущности
  entities/        # игровые объекты: меш + тело + собственное поведение
  effects/         # частицы, пулы эффектов
  input/           # контроллеры ввода
  ui/              # GUI-панели и их стиль
  utils/           # общие утилиты (только реально переиспользуемые)
```

## Производительность: код, выполняемый каждый кадр

Горячий путь — `onBeforeRenderObservable`, `registerBeforeRender`, колбэки физики, обработчики указателя.

- **Ноль аллокаций в кадре.** Никаких `new Vector3()`, `new Quaternion()`, `new Color3()`, литералов объектов и массивов,
  замыканий, `.map/.filter/.slice`, конкатенации строк внутри кадрового кода.
- Вектора и матрицы — переиспользуемые приватные `readonly` поля класса (scratch-объекты) и in-place API
  (`addToRef`, `scaleToRef`, `copyFrom`, `TmpVectors`).
- Объекты, которые появляются и исчезают (осколки, частицы, пули, эффекты), берутся из **пула**, созданного заранее;
  «уничтожение» = возврат в пул, а не `dispose()` с последующим `new`.
- Обходы коллекций — `for` по индексу с закешированной длиной, без создания итераторов и колбэков.
- Подписки на события создаются один раз при инициализации и снимаются в `dispose()`; нельзя подписываться внутри кадра.
- Повторяющуюся геометрию рисовать инстансами/thin instances, а не копиями мешей; материалы переиспользовать.
- Проверять глазами и профайлером: Babylon Inspector, Spector.js, вкладка Performance. Бюджет кадра — 16 мс.

## Дублирование

- Второе появление одной и той же логики — сигнал выносить: общий базовый класс, отдельный сервис или утилиту.
- Copy-paste между сущностями запрещён; общее поведение мешей с физикой живёт в базовом классе.
- Любой источник одного и того же эффекта (удар, луч, таймер) вызывает **один** метод-исполнитель, а не свою копию логики.

## Чек-лист перед коммитом

1. `npm run build` — зелёный, без предупреждений типов.
2. Приложение запускается, фича проверена в браузере (не «должно работать», а посмотрел).
3. В кадровом коде нет новых аллокаций и подписок.
4. Нет `any`, мёртвого кода, закомментированных блоков и `console.log`-отладки.
5. Новые константы ушли в конфиг, новая логика не продублировала существующую.
6. Коммит запушен в GitHub.
